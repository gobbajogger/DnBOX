# Can exact first-write Undo reclaim the 36,420-byte stage?
## Decision
Not by itself, and not by treating the 4,096-byte history cap as a first-write cap. On both current guarded native maps, project_stage is a real 36,420-byte POOL object and undo is a separate 4,252-byte struct including its 4,096-byte entry bytes. The first 40 staged bytes are settings; steady Undo compares the other 36,380 B. Exact source and proof commands below. No firmware modification or newly spendable RAM.

## Actual write, history, transfer and load ownership
- ui.c:4188–4248 initializes the baseline from the whole live project after settings, and commits quiet windows only (no held keys/buttons or recent action; no active recording playback, no transfer or PERF). do_undo and project_acquire also commit at existing boundaries; committing earlier would change gesture grouping. undo.c:66–157 calculates differences against final region. It coalesces changes across up to seven unchanged bytes, includes unchanged bytes between edits for exact swapping, stores first/last offsets and two-byte padding. Size >4096 clears history, not rolling back the edit. Changed run offsets also determine musician-facing labels and engine revision/recorder/typed-control guards.
- The existing full comparison tracks writers that never notify Undo before a store: ui.c clear_part/clear_lanes/copy_part and notes/motion/step recording; seq/sequencer.c seq_rec_bass/cancel audio-owned pattern/lock updates; remote_dnr3.c writes early into the real motion array; smc_mixer.c adjusts persisted FX; original presets may commit bank/tag at an audio boundary, hence undo_commit_stable temporarily holds their adoption. A hook on mark_dirty is too late and also cannot infer field/span. A generic optimized writer requires an exhaustive real writer census and reversion handling before removing shadow; no free IRQ slot/extra audio mute.
- Physical actions stage a destination while record_finish/runtime still matters; undo_undo/redo restore from raw entries and call changed(off,len). The long-hold UI transfer starts by holding audio, rejecting unsafe active edits/notes, then committing a pending gesture. Project stage is exclusively borrowed while undo history remains available. Abort preserves live project and recreates the exact shadow; success commits stage, reinitializes typed engine/IO, and resets history. Reset and device load fill stage before adoption; export captures stable bytes/settings there.
- editor.c ed_project_handle accepts all 36,452 X0XP bytes (32-byte header plus 36,420 payload) sequentially. Unaligned repeated spans must compare against exact bytes already accepted, prior to validation. Until full CRC/layout/migration it accepts arbitrary bytes into the stage, so applying a bounded compressed parsed state would not implement the approved retries. Abort after sample writes may deliberately keep the project/audio hold until old sample hashes are restored. No “just overwrite proj and restore last save” because it loses unsaved data and partial transfers, or changes failure semantics.
- project.c load_stream invokes the old lz.c decoder into the staged patterns+arrangement span, then checks CRC or same-generation tuple and semantic format, then migrates. Backreference distance is 16 bits plus one bounded by produced output, not by the 4 KiB compressor hash. The real decoder witness proves the distinction; not a claim the synthetic raw spans validate as a full preset/project. Avoid any rolling buffer shorter than supported distance unless another storage area retains addressable historical produced bytes.

## Executed proofs
Using actual untouched undo.c/lz.c from the current exact guarded source:
1. 5,000 positions touched, 4,999 returned before the gesture ends: the stock implementation keeps prior history, appends a single 14-byte entry, and the exact undo/redo chain succeeds. A capped “cannot log first touches → clear history” loses that valid history. The fixture is a generic raw-byte admitted Undo region; it does not claim one specific physical gesture triggers those exact writes. In contrast, genuine 5,000 net changed bytes do clear history, retain the modified data and synchronise baseline.
2. A 911-byte encoded input produces 33,668 bytes with a true 24,704-byte distance; malformed before-start reference fails closed. This is below the 15,332-byte stored-stream cap, despite distance far beyond 4 KiB. Stop short rolling-window plans.

## Plausible future arrangement, not counted
* Keep the exact last-commit baseline or build a fully ordered writer transaction scheme with genuine reversible operations plus before-images, including old code's final-net no-op test and history entry format. A bounded small ledger alone cannot guarantee arbitrary coalesced gestures; disjoint data such as two drum kits × 11 tracks × 64 steps × 32 patterns already contains 5,632 bytes of potentially unsaved hits. Streaming before-images to user storage or adding a save/flash write is outside scope.
* If the steady Undo shadow ever moves, the existing 66,240-B display buffer *might* temporally house an aligned 36,420-B full project object in its suffix during project acquisition; 29,820 B remain at front (62 full rows), and normal project_busy draws only the 20-row header. This is not proven: before any such alias need actual lcd_sync at acquisition (previous full-row DMA might still read), renderer/mode/IRQ/recovery/OTA takeover and reset/abort proof, preserve stage pointer alignment and both generation checks. SCRATCH can still be live with transport chunks and must not be borrowed silently.
* An 82-row canvas is 39,360 B. Beside existing 9,600-B header raster it is at least 6,660 B too small for the full stage. Reusing the suffix and also claiming all canvas savings would double-count. Separately shrinking only the busy header to ≤6 rows or staging across separately proven lifetimes is an architecture proposal, not an admitted saving.
