# APP/storage architecture: recover occupied VM sectors without shrinking audio
This is a source/sector proof and offline model, not a native firmware fit, migration implementation, or device result. Exact restored firmware at the old build SHA and durable complete-controls receipts are not interchangeable: the current build previously used essentially all FDATA, SLOT3 and FITTAB, and the currently present linked 73749f55 ELF is only an example corpus.

## Auditable physical geometry, both SMK37 boards
The shared hard addresses come from `firmware/hal/fm1_flash_map.h`, `firmware/src/storage.c`, `project.c`, `panel.c`, `engine.h`, and `boot_screen.h`. Preserve the contiguous APP code capacity 552,672 B, BLE encrypted 64 KiB, user trim/cal/BTIF, OTA staging/config/keymac, boot pairs, and fixed sample-slot starts.

### Acquisition options
1. **Conservative 8 KiB net plain capacity**: store exact current and previous PANEL and SETTINGS payloads in one CRC-checked A/B journal using existing SETTINGS pair. After migration and rollback backup, release 0xA5000–0xA6FFF to immutable build data or the removable pool. One data page plus one commit page per worst settings or calibration edit (224-byte body; 480-byte span including padding), as today. SOUND and all existing previous versions stay untouched. This is not the existing sample/Chicago codec saving.
2. **Expanded 16 KiB gross plain capacity**: use original SOUND A/B for single CRC-checked checkpoint carrying current SOUND plus current and previous PANEL/SETTINGS. With 16-byte typed descriptors the body is at most 2,956 B; physical occupied span 3,212 B per sector, 884 B spare even at worst payload. The active and immediately preceding committed complete checkpoints coexist; every interruption retains the old complete tuple or new complete tuple. Independent old SOUND history can get superseded after two small settings-only changes (old production invokes previous-copy API only for pattern stream, not SOUND). If keeping historical sound recoverability is a requirement, ship conservative option or independently qualify a bounded history codec, not an unbounded delta assumption. Expanded naive writer moves up to 12 data pages instead of one on settings-only write; do not adopt until wear/foreground-latency budget is measured (an append-only tiny overlay inside sector-tail is an optimization requiring its own recovery state machine).
3. **Optional whole 4 KiB owner sector**: conserved only if validated new A/B header incorporates mandatory owner tag with identical foreign-store refusal. Never append immutable APP bytes after old owner tag inside same erase sector; old clear erases it. This is a separate migration, not earned space. Net plain is then 12/20 KiB, only if validated.

### Cross-region ledger / honest boundaries
- Sectors are not contiguous with APP due to BLE. They cannot enlarge the executable XIP limit. Candidate data destination is plain read-only companion XIP; every APP relocation must charge bytes, header/CRC, sector alignment, installer and native timing. Keep audio hot state and code where it is in this first change. Alternatively attach sectors to removable storage; the same sector cannot do both.
- Old real linked layout includes losslessly relocatable UI assets such as 1,385 B `DV_XY_PACKED`, 243 B `DV_POLY_PACKED`, 504 B `arc8_turns`, 252 B `arc8_pixels`, 333 B `UI_PICTOGRAM_LOW`, 249 B `CFG_DESC`, 296 B `FONT_ALPHA_SUB`, and 256 B `FONT_ALPHA_PREFIX`: 3,518 B illustrative real old APP ROM before new header/align, **not** claimed as current complete-controls or timing-measured savings. Prefer a fresh native symbol/section map with authenticated data hashes. Do not relocate fallback font or code needed in flash-busy/RAM. The independent timing runner needs to measure exact projected data under cold/loaded UI and audio.
- Alternatively the schedule workspace's current sector-aligned pooled capacity 36 KiB becomes 44/52 KiB (8/16) if new sectors are dedicated to removable banks; optimistic 120 KiB relocation-all ceiling becomes 128/136 KiB. A 176 KiB full bank corpus still needs 40 KiB at the expanded optimistic ceiling before an update reserve. Presets remain out of APP.
- User data protection is a shipping blocker until verified: read both old copies, distinguish damaged/erased/I/O, fail closed, export exact old sectors plus atomic verified backup before changing any ownership; commit/read back a new journal copy in the old inactive sector without touching the latest old copy. Validate both new generations and interruption recovery before any retired sectors are repurposed. Old firmware rollback must restore original full sector backups before boot, not assume old readers understand new layout. Extend only explicit write windows, preserve protected regions and asset sectors across foreign-owner clearing; refuse unknown versions. Use safe flash maintenance, not transport/live audio. No device writes or migration tooling performed.

The offline model `vm_proof.py` tests cut at every prefix position in erase/body/commit phases for three expanded and two conservative updates (29,891 positions total). It only checks abstract two-sector atomicity with exact payload lengths; it does not simulate arbitrary flash electrical behavior, write-window changes, native link, flash latency, firmware migration or installer rollback.

### Supported downgrade and ownership
A new format-specific owner marker is necessary but **does not** protect one from an old build: old st_owner_check() explicitly erases the VM below XDATA on another family (historical vendor test protects only boot/FDATA companions); old st_save also directly erases/progs the fixed odd/even SET/PANEL addresses even with a usual old-family tag. Therefore:
- Until compatibility exists, reserve retired sectors only as restorable immutable assets, not as the sole copy of any user banks. Backup is not permission to advertise legacy-install safety. Putting user-controlled banks there requires a new installer with no blind force or old-browser fallback and verified full-layout backup/restore support; arbitrary out-of-band old flash restoring invalidates the guarantee.
- Supported migration: hold flash writes, take a complete legacy backup with both A/B generations, tagged layout/board identity and hashes; reread and compare all manifest-protected sectors. Write new SOUND journal to the inactive sound copy. Re-read byte/CRC and boot new APP in recoverable mixed-format mode; only then write its second complete checkpoint and verify both. Keep legacy SET/PANEL physically untouched until acknowledged new layout is live and rollback backup is present. Enable new protected immutable extents only under the new flash-map/application/installer identity; refuse stale-package geometry.
- Supported downgrade must restore exact legacy pair/owner sectors while the new app or installer still owns flash, verify readback, and only then select/boot the old app. The installer must first export newly authored user banks and take a new atomic checkpoint; do not use the original legacy backup as a substitute for preserving later edits. Old records should use original bytes on rollback, not recode possibly unknown small fields. The original individual payload headers and two validated generations remain in that rollback pack; reconstruct latest values only when the user explicitly requests migration, with unrecognized layout rejected.
- No protocol here can make unsupported flash tools running stock or old firmware erase-safe while still writing those physical sectors. Without a ready migration/downgrade installer and a native linked receipt, executable APP recovered/validated today is **0 B**. The defensible **geometry opportunity** is +8 KiB conservative or +16 KiB expanded. The 4 KiB owner sector is a later separate delta, not part of current claim.
