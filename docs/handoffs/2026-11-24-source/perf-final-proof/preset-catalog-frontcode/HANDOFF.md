# 694 + 640 resident versus seek-cache accounting

Authenticated current sources only: the production C reader decodes 694 installed Synth One records with 99,936 ordered binary32 fields, and the approved 640 SuperJ6 corpus with 90,549 ordered fields is the existing independently identified local export. No use of the inaccessible new ZIP. The reported 906 + 640 expansion has 212 more Synth One presets, so its 167,336 B is not a measured result for this installed corpus. No raw words, UUIDs, names, preset bytes or audio persisted by this experiment.

## Independent small catalog codec

The existing ordered bank/name representation can keep only one previous name (in the caller's output buffer), restarting at fixed-size bank blocks. Compact the exact front-code prefix and suffix lengths into two nibbles and use explicit bytes only for an escape. UTF-8 is treated as exact bytes, not normalized. Published order is the local authenticated corpora, with bank title, first authored position, pinned corpus identity and exact count; this does not supersede the separate original-release-ordinal crosswalk. Distinct names are not assumed.

Fixed header and registry bytes are charged, not represented by a shipping parser. Optional literal per-program UUID table is 21,344 B; UUID lookup and bank parsing/CRC are not included in the name decoder cost. S1 and J6 names are known exactly, sampled in shuffled read order and all 1,334 independently decoded for every restart length with compiled C. Invalid offsets and insufficient destinations rejected. No audio I/O or firmware runtime touched.

The standalone PI32v2 name decoder is 224 B text, zero data/BSS. Native disassembly saves 11 words (44 B) and uses five existing caller stack argument words (20 B); no local allocation or heap. Maximum caller-owned output is 37 B including NUL; decoder component needs roughly 101 B including output/ABI, before outer validated-container and call frames. This is not a full linked target, new RAM permission, or word-codec estimate. A 32-row catalog very narrowly fits 20 KiB only as names/ordered IDs (16 B left), and 24 KiB fits all four variants with pinned ordinals only. The 16 KiB budget fails this codec by at least 4,080 B. An older unbounded whole-stream LZMA name calculation at 10,903 B makes 16 KiB plausible for a different approach, not demonstrated for the needed cold RAM/seek form. Full UUID catalog does not fit even 24 KiB. A process can show a small subset of names without proving the repository of all controls fits.

## Whole words and caches are different

The proposed 16/24/20 KiB totals exactly 61,440 B, before any cross-region headers not already charged. The separately reported 79,195 B exact 640-J6 word payload (UUID mapping separate) exceeds the entire current legal capacity by 17,755 B even if every other item were free. Adding the independent tuned 61,052 B S1PK is 140,247 B **before J6 metadata**, 78,807 B over. The verified older 68,000 B J6-only float stream is deliberately incomplete (unbounded and before metadata); with tuned S1PK it is 129,052 B, also red. The existing tuned S1PK alone covers 694 and leaves 388 legal bytes before currently enforced erased-tail/container requirements. Do not sum the measured 20,464 B catalog blindly onto S1PK: S1 names already partly included, and gross size already fails before that distinction. These are concrete measured envelopes, not an information-theoretic impossibility. Existing exact dual-bank empirical optimistic estimate 81,759 B lacks real model and restart tables, and prior actual 143,407 B arithmetic prototype omits literal UUIDs; neither provides a product-ready alternative.

As working windows, 20 and 24 KiB can each stage an 8- or 16-record exact block from either current corpus with explicit one-byte field ID, four-byte word, 16-byte UUID and name, before extra parser buffers: the measured maxima for 16 are 12,137 B Synth One and 13,237 B J6. At 32, S1 uses 24,248 B (fits 24 KiB but not 20 KiB) and J6 uses 26,405 B (neither); these are raw block working-set numbers, not compressed resident bytes or a recommendation to allocate native RAM. A one-record J6 field tape peaks at 835 B even before name/UUID; one-record streaming is mechanically viable for the tape but not inferred safe at the current native POOL floor. Finite caches alone cannot access the uncached records without verified other local persistent backing. Browser or remote fetch is not an all-preset-offline promise. No flash map, firmware/decoder, calibration, package or user resources changed; engine completeness and original sound/timing qualification are separate gates.
